# Findings

What this benchmark has established, what it falsified, and what it learned
about measuring itself. `RESULTS.md` holds the numbers and is generated by
`--summarise`; this file holds the reasoning, which a table cannot carry.

Campaign of 2026-08-19/21, on `prime` / `test-0.1` (280 queries, k=20),
metrics from the official `stark_qa` evaluator.

**Read §8 before comparing any two numbers.** Retrieval became
index-backed on 2026-08-21 and every arm was re-run at
`hnsw.ef_search = 800`; rows in `RESULTS.md` carry a `retrieval` column
saying `exact`, `hnsw/ef=N`, or `--` for reports written before the
provenance block existed. A number on one basis is not comparable to a
number on another, and the difference is larger than several of the
effects reported below.

---

## 1. Relational text is worth a great deal — through the lexical channel

**The finding.** Two arms, same embedding model (`qwen3-embedding-0.6b`),
same ~1.0 chunks/node, differing only in whether the indexed document carries
a `- relations:` block naming the node's neighbours:

| agent | no relations | with relations | change |
|---|---|---|---|
| dense | 0.18274 | 0.18664 | **+2%** |
| lexical | 0.20479 | 0.24913 | **+22%** |
| hybrid | 0.19870 | **0.28214** | **+42%** |
| rerank (fetch=20) | not run | 0.41948 | — |
| rerank40 (fetch=40) | not run | **0.46323** | — |

`qwen-rel-whole` + `rerank40` at **0.46323 mrr / 0.40000 hit@1** is the best
figure this project has produced — nearly double both `vss-control`'s best of
0.23111 and STaRK's published ada-002 VSS figure of 0.2350. See §1a for what
the width actually bought.

**The mechanism, which was not predicted.** PRIME's queries name related
entities verbatim: *"a drug that targets X and is indicated for Y"*. Those
names appear in the answer's own document **only** in the relations version.
BM25 matches them directly; a single dense vector compresses them away. So
nearly the whole gain arrives through the lexical channel, and dense barely
moves.

**Retrodiction it explains.** Across the older arms, `lexical` beat `dense`
on 5 of 9 configs, which read as noise. It was this effect showing through
weakly on corpora that lacked the relational text — and the clearest
exception was `vss-control`, which has the largest dense margin in the table.

**What follows for the architecture.** A knowledge graph's edges are worth
more as *text in the index* than as a traversal at query time, at least on
this benchmark, and worth most to the retrievers that can match a name
exactly. That is a result about how to use a graph, not about how good the
graph is.

## 1a. The reranker's ceiling was the binding constraint, and it broke

`rerank` fetches exactly `k`, so the set it returns is `hybrid`'s **by
construction** and `recall@20` cannot move. That makes it a pure ordering
experiment, and it was a good one: 0.28214 → 0.41948 mrr from reordering
alone. But it also meant every gold answer hybrid ranked 21st or worse was
permanently unreachable, whatever the model did.

Fetching 40 and returning 20 lifts that:

| | fetch=20 | fetch=40 | change |
|---|---|---|---|
| mrr | 0.41948 | **0.46323** | **+10.4%** |
| hit@1 | 0.35357 | **0.40000** | **+13.1%** |
| hit@5 | 0.50357 | 0.53929 | +7.1% |
| **recall@20** | 0.46508 | **0.53693** | **+15.4%** |
| seconds | 5,162 | 10,079 | +95% |

**recall@20 moving is the whole result.** It was frozen at hybrid's 0.46508;
the reranker promoted enough real answers out of ranks 21-40 to add 15.4%
more gold to the returned set. On **69.2%** of queries the returned set
differs from hybrid's, so the wider window is used heavily rather than
decoratively.

**The predicted downside is real and was outvoted, not absent.** A wider
fetch lets the model demote a marginal hit off the end as well as promote one
up, and a 4-query probe had shown exactly that — a gold answer at rank 18
pushed out. Demotions still happen here; they are simply outnumbered. Do not
read this as "wider is always better": at `fetch=60` the balance could
invert, and the experiment that would say so has not been run.

**Cost is the caveat.** Doubling the window cost ~95% more wall time — 35.9
against ~18.4 seconds per query — and against `hybrid` it is **40x the wall
time for +64% mrr**. Prompt cost is not linear in candidate count, so a third
doubling should be costed before it is scheduled rather than assumed.

### Two measurement errors from this run, both of which produced wrong answers

- **`checkpoint_every = 25` makes the predictions file a step function.** A
  4-minute window landed entirely between two flushes and read *zero*
  progress, which looked like a hang. This is the same defect CLAUDE.md
  documents for `CHUNK_BATCH`, in a different unit, and it was walked into
  anyway.
- **A window must outlast the variance it samples — "use a window" is not
  sufficient advice.** One 25-query step timed **8.8 s/query**; the whole-run
  average was **35.9 s/query**. The short window was 4x optimistic and was
  believed precisely *because* it was a window rather than an
  elapsed-over-total. Per-query cost swings with candidate document length —
  40 candidates at up to 2,000 characters is an 80,000-character prompt on a
  dense node — so 25 queries is a sample, not a measurement. A 100-query
  window agreed with the whole-run average to within 2%.

### A failure check that did not need the log

This run's stderr was piped into `tail -40` and lost. The failure that
matters — every `extract` call failing, which makes the agent return
retrieval order and therefore score *identically to `hybrid`* — was still
detectable, because `qwen-rel-whole.hybrid.predictions.json` was on disk:
**3 of 250 queries (1.2%)** had a top-20 order identical to hybrid's, and
none were empty.

Comparing against a sibling arm's predictions catches the defect by its
**effect**. The log line catches it only if the exception was raised, caught
and logged as expected. The first is the stronger check, and it costs
nothing.

## 1b. Relational text only helps if you choose *which* relations

The strongest result of 2026-08-20, and it inverts the obvious reading of
finding 1.

`rerank40title` sends each candidate as `name (type)` and nothing else --
~37 characters against a full document's 3,415. The two arms below add
**eight neighbour names** to that (one per relation type, capped at eight
types), identical in count, in shape and in token cost. They differ only in
*which* eight: document order, or BM25 against the query. Measured on real
candidates, the kept names differ on **48.2%** of them.

All four arms: `qwen-rel-whole`, `test-0.1`, k=20, fetch=40,
`gemma-4-26b-qat`, official evaluator.

| passages shown to the reranker | mrr | hit@1 | hit@5 | recall@20 |
|---|---|---|---|---|
| none (`hybrid`, no reranking) | 0.28214 | 0.1679 | 0.4286 | 0.4651 |
| title only | 0.33975 | 0.2536 | 0.4500 | 0.4721 |
| **+8 relations, document order** | **0.31010** | 0.2071 | 0.4643 | 0.4719 |
| **+8 relations, BM25-ranked** | **0.39343** | 0.3071 | 0.4964 | 0.5067 |

**Arbitrary relational text is worse than none.** Adding eight neighbour
names chosen by document order costs **0.030 mrr** against showing no
relations at all, and hit@1 falls from 0.2536 to 0.2071. Choosing the same
number of names by BM25 gains **0.054** over titles. The swing attributable
to selection alone is **+0.083 mrr**, roughly eighty times the run-to-run
noise floor established in B-LLM-RUN-NOISE-1.

So "more context helps the reranker" is false here. Names of entities
unrelated to the query are noise the model spends attention on, and it
mis-ranks as a result.

### Why this does not contradict finding 1

Finding 1 measured *whole* relation blocks reaching the retriever, where
BM25 does the selecting at retrieval time -- the matching neighbour names
are why those documents scored. Nothing had to choose.

Reranking on a lean encoding removes that: eight names must be picked
before the model sees anything, and the picking is the whole signal. The
two findings agree on the mechanism (neighbour names matter, lexically) and
differ on what carries it (retrieval scoring, versus an explicit selector).

### What it implies for the next arm

The selector, not the channel, is where the value is. That reverses an
argument made earlier the same day: relations moved lexical +22% and dense
+2%, which suggested a dense selector would be dead weight. That reasoning
was about the *channel*. This result is about the *selector*, and it shows
selection is worth 0.083 -- so a better selector is the highest-value lever
available, and the embedding-plus-BM25 hybrid is worth its port addition.

Two cheaper things are untested and should come first: `per_type` and
`max_types` have never been varied, so we do not know whether eight ranked
names is near a plateau or on a steep part of the curve; and recall@20 rose
0.4651 -> 0.5067 as `fetch` went 20 -> 40 without flattening.

## 1c. Chunking helps the lexical channel a lot, and we predicted otherwise

`qwen-rel-sliding1k` -- the arm ingested to answer "does redstring's
chunking help on the corpus that matters" -- against `qwen-rel-whole`. Same
model, same corpus, same tenant scheme; the only difference is
`sliding-1000-500` versus `whole-document`, 4.250 chunks/node against 1.002.

| metric | whole-document | sliding-1000-500 | change |
|---|---|---|---|
| mrr | 0.24913 | **0.32131** | **+0.072 (+29%)** |
| hit@1 | 0.18214 | 0.23929 | +0.057 |
| hit@5 | 0.33571 | 0.42500 | +0.089 |
| recall@20 | 0.33724 | 0.40363 | +0.066 |

**The config predicted this would not happen.** Its own comment, written
before the run: *"Lexical may DEGRADE, or not move. BM25 already sees every
term in the document whether it is one chunk or four; what changes is the
length normalisation and the per-chunk idf."*

The premise was right and the conclusion was wrong. BM25 does see every
term either way -- but length normalisation is not a detail here, it is the
mechanism. A matching term in a 12,000-character document is heavily
discounted; the same term in a 1,000-character chunk is not, and
`aggregation: max` lets the node take its best chunk's score.

Supporting evidence, splitting the 280 queries by how long their gold
answer's document is:

| gold document length | mean change in reciprocal rank |
|---|---|
| shortest third (median 959 ch) | +0.061 |
| middle third (median 3,846 ch) | +0.055 |
| **longest third (median 14,326 ch)** | **+0.101** |

The gain is broad but roughly 1.7x larger where the gold document is
longest, which is what length normalisation predicts. It is not the whole
story -- the shortest third gains substantially too -- so treat this as
consistent with the mechanism rather than as isolating it.

### Why this did not show up in the earlier chunking sweep

FINDINGS 3 measured chunking on `prime`, where documents carry no
`- relations:` block. Median document there is 103 characters against
`prime-rel`'s 357, and the long tail is far shorter. Chunking cannot help
length normalisation on documents that were never long enough to be
penalised. **The chunking sweep answered its question for the corpus it
ran on, and that corpus was the one where chunking had the least to do.**

### Standing caveat

Only the LEXICAL arm is measured. `dense` and `hybrid` on this corpus need
the embedding endpoint and are unrun. The config's other prediction -- that
dense may IMPROVE, because a 1000-character window isolates the relations
block into its own chunk for the 19.5% of documents over 2,400 characters
-- is still open, and it is the more interesting half.

Worth noting for scale: `qwen-rel-sliding1k` lexical at 0.32131 already
beats `qwen-rel-whole` **hybrid** at 0.28214.

## 2. The hypothesis this campaign falsified

`qwen-wholedoc` dense (0.183) against `vss-control` dense (0.231) was read
here as **"ada-002 is reading a richer corpus"** — the theory being that
STaRK's precomputed vectors are over `add_rel=True` documents while every
local arm embedded `add_rel=False` text.

That theory redirected a day of endpoint time. It is **wrong**. Giving qwen
the relational text moved dense by **0.004**, leaving the gap to ada-002
essentially intact.

So on the dense channel, ada-002 is simply better here than
`qwen3-embedding-0.6b`, with one standing caveat: **every local number is for
a Q8_0 GGUF served by llama.cpp**, not for the model as published. See
`B-ADA002-PROVENANCE-1` for what remains unverified about STaRK's own
embeddings; it no longer changes any conclusion of ours.

**The arm was built to test a hypothesis, the hypothesis lost, and the arm
produced the project's best result anyway** — for a mechanism nobody
predicted. That is the case for building the cell rather than arguing about
it.

## 3. `boundary-preference` is an outlier, now on three models

redstring's own default chunker came **last on dense retrieval** on Nemotron,
and again on qwen's mini set. `sliding-1000-500`, at more than double the
granularity, beat it both times. `RESULTS.md` finding 4 previously ruled out
the two obvious explanations — not lost content, not chunk length.

Three models agreeing points at the chunker rather than at an interaction
with one embedding model. This is the most concrete thing this benchmark has
found *about redstring*, and it deserves a passage-level diagnostic rather
than another arm.

Not yet tested on `prime-rel`, deliberately: re-testing a three-time loser
was judged lower value than measuring the winner on the corpus that matters.

## 4. What we learned about measuring this system

Every entry here cost real time, and each is a trap that will be walked into
again by anyone who does not know it.

### A snapshot cannot distinguish stalled from busy

A healthy ingest was diagnosed as hung on four signals that all looked
damning and were all misreads:

| signal | why it was wrong |
|---|---|
| log had stopped | `ingest done` prints *before* the 8.1M-edge phase, which logs nothing (`B-EDGE-PROGRESS-1`) |
| chunk count flat over 30s | chunks commit in `CHUNK_BATCH = 1000` steps; on long documents a flush is ~6 minutes apart |
| client CPU unchanged over 20s | an I/O-bound client accrues under a second in 20s |
| `/slots` showed `processed: 0` | that is what a slot reports the instant it picks up a task |

What settled it: `id_task` climbing across three samples, and a 3-minute
window showing +5,010 chunks. **Only a window measures a rate.**

### Extrapolate by characters, not documents — and even that has a caveat

A `--limit 3000` calibration implied a 6.5-hour arm; the truth was ~2. The
head of `prime-rel` averages **5,278 chars** against the corpus mean of
**1,761**, and `--limit` always samples the head.

The engine's own ETA has this bug: it counts nodes, so it read 152 → 180 →
**198 minutes** while the arm was 11% through its nodes and **28.9% through
its characters** (`B-RATE-UNIT-1`).

But characters are not a constant rate either. Attention is quadratic in
sequence length, so a 1,024-document slice averaging 5,278 chars measured
1.94M chars/min while whole `prime-rel` sustained ~720k
(`B-QUADRATIC-DOCS-1`).

### Assert on the data, not on exit codes

Every check that caught something real this campaign was a data check:

- `total_chars = 227,851,132` — **exactly 100.00%** of the corpus, proving the
  rel arm splits rather than truncates
- `edges = 8,100,498` — exactly `edges.jsonl`'s line count
- `nomic-wholedoc` and `qwen-wholedoc` both score lexical **0.20479**,
  identical to five decimals, because BM25 does not see the embedding model —
  an unplanned confirmation that tenant isolation is clean
- a warm-cache arm scoring `0.3590479185937771`, byte-identical to its
  pre-cache figure

And one CLAUDE.md warning that was **stale**: `self_loops_dropped: 0` is the
correct answer for the current PRIME export, which contains no self-loops in
any of its 8,100,498 edges.

### The helper works, nobody calls it

Shipped twice in one session historically, and guarded against twice more
this campaign. Deleting `embedding_cache=` from the CLI call site leaves
**all 212 other tests green**; only an AST check on the call site catches it.
Same for the `enable_thinking: False` flag, which was protected purely by a
library default and had no test at all.

**Break the implementation on purpose and watch the suite go red.** Every
test added this campaign was verified that way, including two that caught a
vector/text misalignment — the defect that fills a store and scores like
noise.

## 5. Cost, and what it bought

| | |
|---|---|
| ingest, `prime-rel` whole-document | 61 min, 129,375 nodes, 100.00% of text |
| edge load, 8.1M relationships | ~28 min, silent |
| `dense` / `hybrid` / `lexical` scoring | 1-5 min each |
| `rerank` scoring | ~35 min, 1 LLM call/query, **0 extract failures** |

**The embedding cache** (`kg_embedding_cache`, keyed on
`(model, document_prefix, sha256(text))`) measured on `prime-mini`:

| case | wall | hit rate | speedup |
|---|---|---|---|
| cold | 293.8 s | 1.7% | — |
| same config again | **14.1 s** | 100% | **21x** |
| different chunker | 409.3 s | **44.7%** | ~1.45x |

The third row corrected an estimate of mine that was too rosy. I predicted a
three-chunker sweep would cost roughly one endpoint pass, reasoning from 86%
of `prime` being under 1,000 characters. **Hit rate is per chunk, not per
document**: a finer chunker emits 2.43 chunks/node against 1.20, and every
extra chunk is a guaranteed miss.

Where it pays enormously is re-running the *same* configuration — crash
recovery, re-scoring after a code change, re-ingesting a tenant.

## 6. Bugs found in redstring and in this harness

Finding these is a legitimate output of this project.

1. **`WholeDocumentChunker` ignored `max_chunk_size`** (this repo, fixed).
   The ingest engine's re-split exists so a character cap need not be guessed
   right; against a chunker that ignores the cap it halves four times,
   re-chunks identically, and raises the provider's error instead of the real
   one. It was a **guaranteed no-op for the chunker that most needs it**,
   because the arms using whole documents are exactly the arms feeding a
   context-limited server. Killed a 46-minute ingest on `prime-rel`'s
   133,778-character outlier. The engine now also raises immediately if a
   halving fails to shrink anything.
2. **`BoundaryPreferenceChunker` degenerated to 1-character advances**
   (redstring PR #64, merged). Found by looking at the data — "does any
   document justify 1,018 chunks averaging 147 characters?"
3. **`SlidingWindowChunker` emits one fully-redundant tail chunk** per
   document longer than the window whenever overlap > 0
   (`B-SLIDING-REDUNDANT-1`).
4. **`EmbeddingProvider` could not express task prefixes.** Design gap, since
   closed by redstring ADR 0043.

## 8. Retrieval was a sequential scan, and the ordering was why

`redstring`'s `PostgresChunkStore` ranked semantic candidates with

```sql
ORDER BY 1 - (embedding <=> $2::vector) / 2 DESC, id ASC
```

which is the same order as `ORDER BY embedding <=> $2 ASC` — the score is
monotonically decreasing in the distance — but is **not a form any pgvector
index can serve**. `hnsw` and `ivfflat` answer the plain distance ascending
and nothing else. So every dense query took a parallel sequential scan and a
full sort over the tenant: 549,697 rows and 2.25GB of vectors per query on
`qwen-rel-sliding1k`, at ~950MB/s, which is the memory bandwidth that number
implies rather than anything being broken.

**The first attempt to fix this made everything worse, and is the more
useful half of the finding.** Three partial HNSW indexes were built (5.7GB,
~9 minutes) against the unchanged ordering. All three ended at
`idx_scan = 0` — not one query used them — and `qwen-rel-sliding1k` dense
went from 165.8s to **519.1s**, a 3.1x *slowdown*, because 5.7GB of unread
index evicted a 2.25GB table from the page cache.

Two verification lessons, both paid for:

- **`EXPLAIN` on a query you did not write is not evidence.** `EXPLAIN` of
  `ORDER BY embedding <=> $1 LIMIT 20` showed `Index Scan using ..._hnsw_...`
  and looked conclusive for an hour. The adapter issues a CTE with a rescaled
  score, a `min_score` filter and a join, and plans as a sequential scan.
- **`pg_stat_user_indexes.idx_scan` is the check with teeth.** It cannot be
  argued with, it needs no query-shape reasoning, and it went from 0 to 280
  for a 280-query run the moment the ordering was fixed.

The fix is one clause in each of two adapters (redstring PR #71). The `id`
tie-break is kept: it is a secondary key over an indexable leading one, so
Postgres takes the order from the index and resolves ties with an
Incremental Sort above it.

### Recall is now a configuration value, and the default is wrong for us

`hnsw.ef_search` decides how wide the graph walk is. Measured on
`qwen-rel-whole`, 280 queries, against the exact scan:

| `ef_search` | wall | mrr Δ | hit@1 Δ | hit@5 Δ | recall@20 Δ |
|---|---|---|---|---|---|
| exact (no index) | 43.1s | — | — | — | — |
| 40 (default) | 1.0s | −0.00318 | −0.00357 | −0.00357 | −0.01171 |
| 200 | 4.6s | −0.00395 | −0.00357 | −0.00357 | −0.00089 |
| 800 | 6.3s | +0.00016 | 0 | 0 | 0 |

At 800 the retrieved sets match the exact scan to every digit. The default
40 is 43x faster than exact and loses 0.0117 of recall@20 — larger than
several differences this project reports between architectures, and
invisible in any artefact until `retrieval_is_exact` and `hnsw_ef_search`
were added to the cost block.

### The knee moves with corpus size, and that nearly cost the campaign

The table above is `qwen-rel-whole`, 129,656 rows. Repeated on
`qwen-rel-sliding1k`, 549,697 rows, against its own exact baselines:

| `ef_search` | dense mrr Δ | hybrid mrr Δ | dense wall |
|---|---|---|---|
| 200 | **−0.01102** | **−0.01042** | ~30s |
| 400 | −0.00281 | −0.00052 | 7.3s |
| 800 | +0.00026 | +0.00246 | 8.0s |

**200 costs 2.8x more on the larger corpus than the sweep predicted** —
0.011 mrr, which is larger than the entire measured effect of several
architecture changes reported here. The campaign had standardised on 200
off the small-corpus sweep and had started the LLM arms, which consume
retrieval output and would have inherited the loss; they were stopped and
restarted after this was measured.

There is no speed argument for the lower setting either: dense is 8.0s at
800 against ~30s at 200, because a wider graph walk still beats scanning
2.25GB of vectors. The positive deltas at 800 are query-embedding
nondeterminism (§9), not the index outperforming an exact scan.

**This campaign standardises on `ef_search = 800`.** Every arm is run on
that basis, so the arms are mutually comparable; they are **not**
comparable to numbers recorded before this change, and the reports carry
`hnsw_ef_search` and `retrieval_is_exact` so a reader can tell.

The general lesson: **sweep a recall/speed knob on the largest corpus you
have, not the one that answers fastest.**

## 9. Retrieval-only arms are not reproducible either

`FINDINGS` previously held that run-to-run noise was an LLM property and
that "retrieval-only arms are unaffected — no LLM". That is false.

Two runs of `qwen-rel-sliding1k` dense, identical code, identical rows, no
index in either, disagreed on **103 of 280 queries**, moving mrr by 0.000054
and recall@20 by 0.000397.

The cause is upstream of the database. The same text embedded twice against
the endpoint, alone, back to back, returns **different vectors** — max
absolute component delta 3.3e-03, cosine 0.99981. Runs 2, 3 and 4 were
identical to each other and all differed from run 1, so it is the first call
after idle rather than per-call jitter; whether that is batch composition, a
warm-up path, or something else is not pinned down.

The noise source was never "an LLM". It is a batched inference server, and
the query embedder is one of those too. `vss-control` reproducing
`0.23057383129905376` to every digit is consistent with this rather than a
counter-example: its vectors are precomputed and it makes no live embedding
call. That is also why it is deliberately left **unindexed** — it is the one
arm whose exactness is a standing check.

**Practical floor:** a dense or hybrid mrr difference below ~0.0002 is noise.
The LLM floor (~0.001 mrr, `B-LLM-RUN-NOISE-1`) still dominates and is
unchanged.

The cheap fix, unimplemented: query vectors are re-embedded every run while
chunk vectors are cached in `kg_embedding_cache`. Caching the query side
would make repeat runs of an arm exact against each other.

## 10. The lean-encoding arms, and what selection is worth

Four arms built earlier and never run, all `qwen-rel-whole` + `gemma-4-26b-qat`
at `ef=800`, against the two lean arms already scored:

| arm | mrr | hit@1 | recall@20 |
|---|---|---|---|
| `rerank40` (full documents) | 0.46323 | 0.40000 | 0.53693 |
| `rerank40titlerelmatrix` | **0.41771** | 0.34643 | 0.52250 |
| `rerank80titlerelranked` | 0.40486 | 0.32500 | 0.51128 |
| `rerank40titlerelranked` | 0.39343 | 0.30714 | 0.50672 |
| `rerank40titlereldense` | 0.37999 | 0.28929 | 0.49830 |
| `rerank40titlerelhybrid` | 0.37984 | 0.28571 | 0.51491 |

**An embedding selector does not beat BM25 at choosing which relations to
show.** This is the question FINDINGS 1b left open, and the answer is no:
`dense` (0.37999) and `hybrid` (0.37984) both land *below* BM25-ranked
selection (0.39343), and within 0.0002 of each other -- inside the LLM
noise floor, so they are not even distinguishable from one another. The
cheap selector wins.

**Averaging three score axes is worth more than any single one.**
`matrix` at 0.41771 beats the best single selector by 0.024, well outside
the ~0.001 floor. That is the largest gain available on a lean encoding.

**The recall curve has mostly flattened past 40 candidates.** `rerank80`
buys 0.011 over `rerank40titlerelranked` for roughly double the LLM
calls. Positive, real, and a poor trade.

Every lean arm remains below `rerank40` on full documents. Whatever the
lean encodings save in tokens, they lose in ranking quality, and the gap
(0.045 to the best lean arm) has not closed with any selector tried.

### An ordering prediction this falsified

`qwen-rel-sliding1k` was queued first on the reasoning that reranking can
only reorder what retrieval found, and that corpus retrieves the most:
recall@20 0.50420 against `qwen-rel-whole`'s 0.46432. It does retrieve
more, and it **still reranks worse** -- 0.41341 against 0.46323.

More candidates, better recall, worse ranking. That is FINDINGS 1b's shape
again at a different level: the reranker is handed a larger and noisier
pool from 1000-character windows and orders it less well than the
whole-document pool. Retrieval and reranking want different things from a
chunker, which nothing in this project predicted.

## 11. What is worth doing next

1. **`rerank40` on `qwen-rel-sliding1k` versus `qwen-rel-whole`, with the
   reranker held fixed.** §10 records that the higher-recall corpus
   reranks worse, but `rerank40`'s 0.46323 was measured on exact
   retrieval before the index and the sliding1k number at `ef=800`. The
   control re-run closes that, and until it lands the comparison carries
   a basis confound as well as a corpus difference.
2. **A reranker-model A/B.** `--chat-model` makes this one variable:
   `rerank40` on `qwen-rel-whole` under `gemma-4-26b-qat` against
   `qwen3.8-27b-64k-txt`, same corpus, same tenant, same split. It says
   how much of the rerank result is the architecture and how much is the
   served model, which is the first thing anyone will ask when these
   numbers are compared against the paper's `gpt-4-turbo` reranker.
3. **`zero_shot` and `deep` on a live corpus.** Both have been scored, on
   the dead Nemotron arms, and both disappointed: `zero_shot` matches
   `hybrid` while costing an LLM call per query, and `deep` -- ~7.46 calls
   per query against a cap of 8 -- was the worst arm on both corpora where
   it ran. The open question is whether the rel corpora change that, since
   `deep`'s `neighbors` tool would have relational text to walk. Needs
   `--ingest-edges` on a live tenant: the qwen arms have none.
4. **A size sweep on the embedder.** `qwen3-embedding-0.6b` loses to
   ada-002 by 6.4 mrr on the dense channel (16.68 against 23.06), which
   makes the hybrid result more interesting rather than less -- the
   margin comes from corpus construction and fusion, not from the model.
   `Qwen3-Embedding-4B` or `8B` would say whether the dense gap is the
   0.6B or the family. New `embeddings:` identifier, new table by
   construction, full re-ingest.
5. **A Typesense arm, or any engine arm.** Checked 2026-08-21: the STaRK
   leaderboard has *no* search-engine baseline and zero PRIME submissions
   from anyone, and Typesense publishes only throughput and latency, never
   relevance. So there is no number to compare against and the gap is
   real. The agent seam makes it a `Toolset`, not a fork. Two caveats to
   state up front if anyone builds it: Typesense's fusion is
   `0.7*K + 0.3*S` over ranks, **not** RRF, so it is a different function
   rather than a retuning of ours; and its joins are query-time filters,
   not traversal, so the path to a competitive arm is denormalising the
   relations block the way `qwen-rel-whole` does.
6. **MAG**, the corpus-generalisation cell. ~849M chars, ~7h locally.
   Also the place to re-check `ef_search`: §8's rule is to sweep a recall
   knob on the largest corpus you have, and MAG is another order of
   magnitude beyond `qwen-rel-sliding1k`.
7. **A backend re-baseline on TEI or vLLM**, so numbers are for the model
   rather than for a Q8_0 GGUF served by a text-generation engine. Costs a
   re-ingest of every arm, so it belongs with the MAG work.
